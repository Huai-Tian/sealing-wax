## 1. 你在构建什么

微信、QQ、邮件的内容都在厂商手里。本项目不要求任何人换软件:用户在不可信 IM
里互传密文,密文穿过信道,服务器全程只见密文与不可识别的配对份额,永远拿不到密钥。

定位三句话:

- 一次配对(可选保存),之后在该 IM 里直接收发密文;不保存则每次从零、结束即焚
- 两端平等:无组织、无管理员、无策略门、无审计——密钥只属于会话两端
- 一把"只会加解密的钥匙":保存的会话没有任何协商/邀请/识别仪式,点开即聊

背景(写给未来维护者):OTR(生态老化)、miniLock(停更)、GPG(UX 反人类)、age(只做
文件)、p≡p(只做邮件)、StegoSafe(隐写单发)、WaxSeal(保险库+组织管控,两端不平等)。
日常、双向、平等两端、密文直接过信道的格子依然空着。对外可辩护的表述只有三个词:
端到端、两端平等、默认零状态。

## 2. 威胁模型(根基)

**主要方向只有一类对手:不可信信道(IM 服务器与链路中间人)。**

| 我们防御 | 手段 |
|---|---|
| 信道读取 | AEAD 加密 |
| 篡改/伪造 | AEAD 认证 |
| 重放/延迟投递 | 终身流水号 + 收方高水位 |
| 首次配对中间人 | PAKE 暗号(口令错=握手失败) + SAS 顶栏核对(双保险) |
| 协议指纹识别(任何流量被认出是火漆) | 数据帧传输掩码 + 配对帧 PAKE 化(全流量不可识别) |

**设备级防护:能做的有限,且不是主要方向——已确定的手段全部做,但不构成承诺。**

- 保存态:Tink AEAD 信封,主密钥挂 Android Keystore/Strongbox
- 加解密核心在 native(§10):密钥不进 JVM,尽可能防 hook(Java 层注入
  够不着密码学本体)
- 截屏保护:FLAG_SECURE,禁截屏与最近任务缩略图
- 内存纪律:密钥只存 `sodium_malloc` 守护页,退出即清零;日志永不打印密钥/明文
- 云备份:`allowBackup=false`

**尽力而为之外,如实告知用户的边界(明确不承诺):**

- 解锁态设备被完全掌控(root/内核级取证/硬件提取):上述手段可被绕过,
  保存会话的历史密文可能被解
- 通信元数据(谁/何时/多大):IM 本来就有,不在保护范围
- 对端背叛(拍照、改装客户端留存明文):端到端通信的固有限制,任何工具同等级

## 3. 硬性边界(最高优先级)

**判定法:对任何要落盘的字节问一句——"这个字节是为了下一次会话吗?"**
是 → 默认禁止。唯一例外:用户退出对话屏时显式选择保存,且保存物仅限 §6 白名单。

App 内明文只存在于内存与屏幕;落盘只能是密文或账本;明文文件导出只能由用户
经 SAF 显式选择位置,App 不记录导出路径。

## 4. 协议(线上三类消息;数据帧两个类型码)

配对帧(邀请/回复)= 无头 SPAKE2 消息,不携通用头——信道侧与等长随机
字节不可区分。通用头只存在于数据帧(且仅在解掩后的本地副本可见):

```
magic:  4B  "SWX1"     # 固定魔数,快速识别与版本位
type:   1B  0x03 文本密文  0x04 文件密文(0x01/0x02 仅存于内部逻辑,不再上线)
suite:  1B  0x01 = SPAKE2(PAKE)+HKDF-SHA256+ChaCha20-Poly1305   # v1 唯一实现
            0x02 = 保留编号(AES-256-GCM,为算法迁移预留;收到即明确拒绝)
```

payload 按 type:

```
invite:  SPAKE2 消息 A(发起方 32B 份额;无头、无 magic、无 type)
reply:   SPAKE2 消息 B(接收方 32B 份额 || 32B HKDF confirm)
data   (0x03/0x04): 8B 流水号(BE,方向内终身单调) + 12B 随机 nonce + 16B 指纹
           + 4B 片序 + 4B 总片数(数据帧统一携带分片字段,单片=0/1) + AEAD 密文||tag
           (上线前固定头掩码:除 nonce 外 38B 与掩码流 XOR,见"传输掩码")
```

密钥编排:

```
pake_shared = SPAKE2(暗号)                 # 暗号错 ⇒ 输出不一致 ⇒ 握手失败
session_key = HKDF-Expand(pake_shared, "session"‖suite, 32B)
sas         = HKDF-Expand(pake_shared, "sas") → 拒绝采样 → 均匀 9 位(3-3-3)
confirm     = HKDF-Expand(pake_shared, "confirm", 32B)   ← 回复帧携带,
                                                       发起方 finish 时校验
msg_key     = HKDF-Expand(session_key, "msg"‖方向‖流水号, 32B)   ← 按需派生,无状态
mask        = HKDF-Expand(session_key, "mask"‖nonce, 38B)        ← 传输掩码流,每帧独立
nonce       = CSPRNG 纯随机 12B(与流水号解耦)
```

- **无棘轮**:消息密钥按需现算,乱序/补发天然免疫;跨会话保密由零状态保证
- **nonce 纯随机**:人聊终身 10⁵ 条量级,碰撞概率 10⁻²⁰,可忽略;换来"无需任何计数器
  同步"的工程简洁
- **流水号**:仅用于防重放与密钥派生输入;收方维护高水位,旧号拒收。持久化纪律
  (内存优先模型,2026-11 定案):会话全程在内存;未保存会话永不落盘(崩溃=会话
  死亡=密钥消失,无重放可防)。保存会话仅在选定时机同步到信封外的 16B 明文小
  文件(发送预支号+接收高水位,原子写):进入对话屏时预支号段(128 个/次)、
  号段耗尽时、进入后台时(onStop,本 App 高频切 IM,后台被杀是常态)、退出
  对话屏时。崩溃/强停后重开,从预支段末尾继续——跳号无害,绝不重号,
  会话不会因计数器回滚而砖死
- **SAS**:9 位数字 3-3-3,常驻对话屏顶栏(菜单图标左侧;点开=大字+二维码+复制的
  放大卡片);电话念码或当面扫码;**对不上 = 立即中止会话**。MITM 主防线是配对
  暗号,SAS 为终身身份仪表盘(保存会话重开后仍可对账,见 §6)
- **AAD** = 通用头 ‖ 流水号 ‖ 指纹 ‖ 片序 ‖ 总片数(数据帧统一携带,防跨消息拼接与调序)
- **传输掩码(2026-11 定案,破坏性变更,SWX1 编号保留)**:数据帧固定头 50B 中除
  nonce(偏移 [14,26))外全部掩码——区域 [0,14)∪[26,50) 共 38B(恰为 AAD 区)与
  mask 密钥流逐字节 XOR 后上线;密文体不掩(AEAD 输出本就伪随机)。收方流程:
  长度检查 → 读明文 nonce → 派生掩码流 → 解掩本地头副本 → 验 magic/type/suite →
  高水位 → AEAD。AAD 语义不变(仍按逻辑字段值计算,与解掩后头等价)。错会话现
  报 SWX_E_FORMAT(魔数解成垃圾)而非 E_CRYPTO。动机与论证明稿:
  - 日常流量信道侧不可识别:整帧与等长随机字节计算不可区分,消除 "SWX1" 前缀
    与流水号高位零字节特征(base64 呈 "U1dYMQMBAAAAAAAAAA…" 开头的指纹);长度/
    时序仍泄露(长度由填充缓解),此为任何加密的固有边界
  - **PAKE 握手同样换不来解掩能力**:配对帧泄露的只有 SPAKE2 份额——从份额
    反推暗号(在线猜测之外)等价于解椭圆曲线离散对数;pake_shared 只存在于
    双端内存,服务器面对的是与日常数据帧同级的随机字节
  - **配对帧 PAKE 化(2026-11 定案,取代"握手帧不掩"的既定交换)**:裸握手必须
    公开可解析(接收方配对前无钥 ⇒ 识别规则公开 ⇒ 服务器对称可用),配对帧必露
    指纹,且一次配对=永久归因锚点——锚定后续全部掩码流量的归属。PAKE 把识别
    依据变为暗号:服务器无暗号即无判定,配对流量与日常流量同等不可识别。暗号
    熵有限(人脑可记量级)⇒ 必须用 PAKE 而非"暗号直接当密钥"(后者可被离线
    暴力枚举);实现采用第三方 SPAKE2,源码入仓,不自己写
  - **两帧是不可再减的下限**:会话密钥必须掺入两端独立熵,每端至少发出一个
    SPAKE2 份额;单帧无法完成交换。暗号取自双方共同记忆(线下事实),零字节上线
- **长度混淆(可选,默认关)**:逐会话设置,本端个人行为(填充纯发送侧,天然无需
  协商、无需两端一致)。未保存会话:对话屏内开关,内存态,随会话消失;保存会话:
  存入会话配置(§6 信封)。无全局设置。开启后明文填充至阈值再加密——短消息全部
  等长,超阈值照常分段;文件末片同步补齐(.swx 体积只泄露 8MB 桶位)。填充格式
  [明文][0x80][0x00⁺](标记必带 ≥1 个 0x00——防"呀"=E5 91 80 这类以 0x80
  结尾的明文被误剥),收方仅在尾部有 0x00 且前一字节为 0x80 时剥离;只剩 1
  字节空间的分片不填充(base64 长度仍恰为阈值)。阈值默认 1000 base64 字符
  (500/1000/2000/4000 可选)
- 封装:文本信道 base64(单片 ≤ 4000 字符,超长自动分片,分片信息绑入 AAD);
  base64 用标准字母表、保留 = 号、不换行(换行符在跨 App 复制与 IM 折叠中易被吞)。
  文件信道二进制 `.swx` 自描述帧序列,内部分片默认 8MB/片(纯流式内存粒度,
  与 IM 文件上限无关;.swx 始终单文件交付)
- 文件元数据(文件名/大小/指纹)加密在首片密文内,信道侧不可见
- 所有格式版本化:改 suite 只需新 magic 版本号,老消息永远可解或明确拒绝

## 5. 会话生命周期(完整工作流)

```
配对(唯一有仪式感的环节;暗号=双方共同记忆中的线下事实,如共同经历,
          必须一字不差,不可用线上聊过的话题——服务器存档即失效):
A 发起方:  首页点[＋新建会话] → 输入暗号 → 生成邀请码 → 复制 → IM 发给对方
B 接收方:  首页点[加入会话] → 粘贴邀请码 → 输入同一暗号 → 生成回复码
           → 复制 → IM 发回
A 完成:    粘贴回复码 → PAKE 完成,直接进入对话屏(无确认页)
           暗号不一致 = confirm 校验失败 = 报错重试(邀请码不必重生成,
           B 用同一暗号重发回复码即可),永不进入对话
           SAS 常驻对话屏顶栏,想核对随时念码/扫码(仪表盘,非关卡)
B 侧说明:  B 在生成回复码时即已建立会话(两帧下限,B 无配对期确认
           路径);暗号不一致由 A 端拒绝,并由 A 的首条可解密消息
           隐式确认——若 A 迟迟无法解密,B 应退出重试

对话屏(五个动作;输入栏统一,2026-11):
发文本:    打字 → [加密并复制] → 切 IM 粘贴          ← KPI:+1 步
收文本:    IM 里复制密文 → 切回火漆 → 粘贴 → 自动解密进气泡流   ← 粘贴即解密
发文件:    选文件(SAF) → 加密 → 分享 .swx 到 IM
收文件:    导入 .swx → 解密 → 选位置导出(SAF)
翻历史:    直接上滑对话屏(保存会话进入即解密载入;明文仅内存,退出即焚)

结束(两个入口,无闲置超时,无结束按钮):
退出对话屏(返回):
           明文即刻清零 → 从未保存过? → 弹窗[保存这个会话吗?]
             保存  → 输入会话名称(是会话名,非联系人) → 入列表
             不保存 → 全部清零,零状态
           已保存过 → 不打扰
退出 App:  直接清零,无弹窗(进程被杀来不及问;未保存的会话静默消失,这是
           "退出即清零"的既定行为)

下次(已保存的会话):
           首页会话列表(按会话名称排列) → 点会话 → 直接进入对话
           发:打字→[加密并复制];收:粘贴→明文。无配对、无邀请、无识别

管理:      长按会话 → 重命名 / 删除(删除=钥匙+历史同删,不可恢复);
           会话内点顶栏名称亦可改名(仅已保存会话;未保存会话的命名在
           退出保存时)
```

## 6. 持久保存模型(宪法修正案)

原 1.0 的 `persistent_state` 绝对禁令,经 2026-11 所有者决策修订为**默认禁止+显式例外**。
逆转论证:威胁模型收敛为"仅防信道"(§2)后,保存的钥匙对信道对手零增益;设备侧代价
已由所有者知情接受。

- **保存物白名单**(钥匙/会话名称/会话配置装入 Tink AEAD 信封,主密钥挂 Android
  Keystore/Strongbox;双向流水号状态在信封外 16B 明文小文件,同步纪律见 §4):
  `{会话密钥 32B, 会话名称, SAS 9 位(身份对账指纹,非秘密), 会话配置(长度
  混淆开关等,§4), 双向流水号状态, 密文历史/账本(§7)}`
- **保存时机**:仅退出对话屏时弹窗一次;已保存过的会话不再问
- **语义**:一把只会加解密的钥匙。无邀请帧(曾设计的 type 0x05 已否决)、无重协商、
  无自动识别发件人——IM 已显示谁发的,用户点对应会话;粘错会话=解不开,不产错误明文
- **单方保存无效**:对方没存,下次对方解不开;App 明示引导重新配对
- **删除**:任一端随时;钥匙+历史同删
- **代价(写进 App 内知情提示)**:信封泄露=该会话历史密文可解;换机=全丢

## 7. 历史与文件账本

历史是正式功能(所有者论证:开源+钥匙在手,改装客户端本就能解历史,官方功能优于
灰色地带)。铁律:**本地只存密文与账本,明文永不落盘。**

| 消息类型 | 本地存储 | 查看 |
|---|---|---|
| 文本 | 密文帧(小) | 进入对话屏即解密载入气泡流(明文仅内存),退出即焚 |
| 文件 | **不存密文本体**。账本条目=文件名(加密)+密文 hash+指纹 16B+大小+方向+流水号 | 同上;文件本体去 IM 里找 |

文件账本细则:

- **hash = 整个 `.swx` 字节流的 BLAKE2b**(密文 hash,非明文 hash)
- 只存本地账本(hash 不能包含自身,故不随文件走)
- **对账流程**:从 IM 翻出 `.swx` → 导入 → 先算 hash 对账(**无需钥匙**)→
  ✓"就是当时那条"/✗"不是当初的文件" → 再解密导出
- hash 对上 + AEAD 解密成功 ⟹ 明文与当初一字不差
- 代价:IM 清理过期文件后,该文件永久丢失(本地只剩名字与指纹)。不囤密文的交换:
  App 永远轻、永远不需要持久文件访问权(SAF 临时权限只在加/解密那一刻用一次)

## 8. 密码学红线

- **不引入 X3DH / Double Ratchet**(Signal 专利主张,别赌)。本设计无棘轮、无
  skipped-key 机制,离专利区比 1.0 更远;保持这个选择
- **单一 AEAD 套件:ChaCha20-Poly1305(IETF,RFC 8439),不提供第二选择**(2026-11
  定案)。理由:纯软件恒时实现(ARX 结构无查表),四个 ABI 全平台一致可用;libsodium
  的 AES-256-GCM 依赖硬件加速且 armeabi-v7a 无实现,查表软件 AES 有缓存时序泄漏
  ——安全工具宁缺毋滥。双套件买不到"中途换锁"(换算法=两端换代码=重新配对),
  只买到协商复杂度。suite 字节即迁移插槽:收到未知值明确报"不支持的套件",绝不
  产出错误明文;未来迁移=新 suite 编号+新版 App,老消息永远可解或明确拒绝。
  XChaCha20(192bit nonce)评估过并否决:纯随机 96bit nonce 在人聊量级碰撞概率
  10⁻²⁰,不值得为此改线上格式。未来维护者勿"顺手加回"双套件
- 只用成熟实现,不自己写密码学:libsodium 1.0.22 成熟原语(scalarmult /
  hkdf_sha256 / aead_chacha20poly1305_ietf / generichash / memzero / malloc)
  + 第三方 SPAKE2 实现(源码入仓,正式来源;2026-11 为配对 PAKE 化放行)。
  红线不变的部分:不手搓 ECDH,不手搓 PAKE,不把暗号直接当密钥
- nonce 每消息 CSPRNG 纯随机;流水号发送前先落盘,防崩溃重用
- 随机数只从操作系统 CSPRNG 取;普通 random 是致命错误
- 格式规范与测试向量随仓库发布(docs/wire-spec.md + JSON 向量)

## 9. UX 约束与视觉语言

- KPI 唯一:发一条加密消息 ≤ 正常发消息 + 1 步。[加密并复制] 必须是一颗按钮
- 视觉语言:KernelSU / SukiSU Ultra / ProxyPin 同款——**Jetpack Compose + Material 3**,
  首页状态卡片 + 会话列表卡片 + FAB,工具感、干净、无装饰
- SAS = 身份仪表盘(非关卡):9 位数字 3-3-3 常驻对话屏顶栏(菜单图标左侧);
  点击弹出放大卡片(大号数字点击即复制 + 二维码)。MITM 主防线是配对
  暗号(§4),SAS 是终身核对仪表盘,含保存会话重开后的对账
- 对话屏顶栏布局:返回 + 会话名(居左,紧邻返回)+ SAS(常驻小字)+ 菜单
  (三横线,通用菜单样式,后期可承载长度混淆等更多设置项)
- 输入栏 = 单栏(收/发一体,0.8 输入框 + 0.2 右槽):右槽仅两态——空框
  = "+"(展开可扩展入口磁贴:发文件/收文件,未来特殊消息预留;点开收
  键盘),有字 = [加密并复制](Send 图标,微信式出现时机)。密文识别不
  做内容启发式,直接活会话试解(防抖 ~150ms):成功即收文,[解密]按钮
  已删除,收文 = 一次粘贴;失败零副作用(magic 校验先于一切状态推进),
  粘错会话给出诚实报错;E_FORMAT = 普通输入,静默并清除旧提示——提示行是
  当前内容的纯函数,实时随字符变动(唯一例外:Partial 的等待提示在空框
  时保留,等齐分片为止)。试解识别是服务器无
  钥无法运行的判定——与 §4 传输掩码同一条不对称原则(所有者洞察 2026-11)
- 不做发件人识别(IM 已做);会话名称≠联系人(§3)
- 集成面仅:剪贴板 + 系统分享/SAF。无深度链接、无推送、无后台
- 技术底线:FLAG_SECURE(禁截屏/禁最近任务缩略图)、allowBackup=false、
  release 剥离日志且永不打印密钥/明文

- C 核心保持平台无关(host 全量测试强制此纪律,零成本);新平台仅在
  双前提成立时评估(§12)——能力保留,承诺不轻许

## 14. 已知风险(设计者须知)

- **暗号质量是新最弱一环**:暗号太弱/与线上话题重合 → 在线猜测面缩小;缓解:
  输入框明示规则(线下事实、一字不差、勿用网上聊过的话题)。PAKE 使暴力
  只能在线逐次进行,几万量级候选已足够。SAS 核对由"必须关卡"降为仪表盘,
  跳过不再等于裸奔(暗号在前),但主动核对仍是发现配对期外替换的唯二手段
- **保存模式的设备侧代价**:设备被掌控且解锁→该会话历史可解(§2 已出局,但须在 App
  内首次保存时知情提示)
- **文件依赖 IM 存活**:IM 清理过期文件→文件永久丢失,本地只剩账本(§7 既定交换)
- 终端威胁(截屏/输入法/剪贴板)与所有 E2E 工具同级;缓解:FLAG_SECURE、明文仅内存、
  显式导出
- 信道行为不可控:平台可能过滤大块 base64;缓解:分片、文件信道
- 战略风险:主流 IM 若原生上 E2E,消费级价值蒸发——头号监控变量

  文本不含 0x00,无 0x00 尾随的 0x80 永远是明文本体;收方仅在尾部 ≥1 个
  0x00 且前一字节为 0x80 时剥离。满片/仅剩 1 字节空间的分片不携带标记
  (后者 base64 长度仍恰为阈值)。文件信道不变(meta.size 裁剪)。混版边角:
  旧端发的孤立 0x80(room==1)在新端会多出 1 字节,双端同版本即无此问题
- **2026-11 数据帧传输掩码**(所有者决策):固定头 38B XOR 掩码,数据帧整体伪
  随机、不可归因于火漆;破坏性格式变更但保留 SWX1 编号(单用户双端同步升级)。
  握手帧不掩——掩握手鸡生蛋,且接收方可用的识别规则服务器对称可用,配对可识
  别被知情接受。安全论证:明文握手不提供任何解掩能力(缺口=ECDH ≈2^128,盐为
  HKDF 公开输入);两帧握手是无预共享秘密下的数学下限;私钥配对即焚,存档握
  手+事后设备失守不可解。详见 §4
