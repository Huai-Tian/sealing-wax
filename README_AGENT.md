## 1. 你在构建什么

微信、QQ、邮件的内容都在厂商手里。本项目不要求任何人换软件:用户在不可信 IM
里互传密文,密文本身穿过信道,服务器/信道全程只见公钥与密文,永远拿不到密钥。

定位三句话:

- 每次会话从零开始(新密钥对、新配对、新 SAS 核对),结束即焚,手机零残留
- 两端平等:无组织、无管理员、无策略门、无审计——密钥只属于会话两端
- 一台"带加密功能的计算器":打开、配对、加解密、关闭,不留痕迹

为什么这个格子是空的(背景,写给未来维护者的战略上下文):
OTR(生态老化)、miniLock(停更,死于 UX 时代局限)、GPG(UX 反人类)、age(只做文件)、
p≡p(只做邮件)、StegoSafe(隐写单发,无协商,口令模型)、WaxSeal(密文进保险库,
组织管控,两端不平等)。日常、双向、平等两端、密文直接过信道的格子,经 2026-11
全渠道核查无人占据。注意:不要对外宣称"唯一的真端到端"(WaxSeal 密码学上也是
端到端);可辩护的表述只有三个词——端到端、两端平等、零状态。

## 2. 硬性边界(最高优先级)

**零状态原则:任何"为下一次"而存在的字节,都是一个泄密单元。**

判定法:对任何缓存/存储/配置提议,问一句——"这个字节是为了下一次会话吗?"
是 → 禁止,无例外。

App 退出后手机上不允许存在任何本项目数据:无密钥、无历史、无设置副本、
无剪贴板残留(可选清除)。会话内的内存态是唯一合法状态。

明文只存在于内存与屏幕。落盘只能由用户显式导出,App 不记录导出路径。

实现时你会遇到的四个诱惑(都已被设计讨论否决,勿再引入):

```yaml
temptations:
  - 诱惑: "加深度链接让配对更顺滑"
    否决理由: "加密工具教用户点信道里的链接=钓鱼训练;带链接消息更易被 IM 风控过滤"
  - 诱惑: "存本地裸公钥环做密钥连续性(TOFU/known_hosts 式)"
    否决理由: "设备取证可还原社交图谱;首用污染后假公钥被永久记住"
  - 诱惑: "加联系人簿/备注方便下次"
    否决理由: "联系人功能=变相泄密(图谱+时间戳+标注)"
  - 诱惑: "加消息历史提升体验"
    否决理由: "历史=状态=泄密单元;与零状态原则直接冲突"
```

## 3. 协议(线上只有三种消息)

通用头(所有消息):

```
magic:  4B  "SWX1"     # 固定魔数,快速识别与版本位
type:   1B  0x01 邀请  0x02 回复  0x03 文本密文  0x04 文件密文
suite:  1B  0x01 = X25519+HKDF-SHA256+ChaCha20-Poly1305
            0x02 = X25519+HKDF-SHA256+AES-256-GCM   # 为算法迁移预留
```

payload 按 type:

```
invite (0x01):  32B X25519 公钥 A + 16B 随机盐
reply  (0x02):  32B X25519 公钥 B + 16B 随机盐
data   (0x03/0x04): 8B 会话计数器(BE) + 12B nonce + AEAD 密文||tag
```

封装:文本信道用 base64(单片 ≤ 4000 字符);文件信道用二进制 `.swx` 文件。
大文件分片:每片是一条 data 消息,片序号与文件指纹绑入 AAD,收齐拼接。
所有格式版本化:改 suite 只需新 magic 版本号,老消息永远可解或明确拒绝。

SAS 派生:`HKDF(shared_secret, info="sas")` 截 30 bit → 9 位数字,3-3-3 分组
显示(便于电话逐组核对)。MITM 撞码概率 2^-30。**对不上 = 立即中止会话**。

## 4. 会话生命周期(完整工作流)

```
A 发起方:  打开 App → 点"新建会话" → CSPRNG 生成本会话密钥对 →
           屏幕显示邀请文本(base64) → 一键复制 → 切到任意 IM 发给对方
B 接收方:  复制邀请文本 → 切到 App 粘贴 → App 解析校验 → 生成本方密钥对 →
           立即算出共享密钥 → 屏幕显示回复文本 → 一键复制 → 回 IM 发回
A 完成:    复制回复 → 粘贴进 App → 共享密钥就绪 → 双方同屏显示 SAS 短码
验证:     双方带外核对 SAS(电话互念 9 位数字,或当面扫 App 内二维码)
交流:     发:输入文本/选文件 → AEAD 加密+钥链推进 → 密文(base64/.swx)
           → 复制或分享到 IM;收:复制密文/导入文件 → 解密显示(仅内存)
           每条消息推进一次 KDF 钥链(前向保密,捎带在密文信封里,零额外消息)
结束:     退出或闲置超时(建议 15 分钟) → 内存密钥与明文清零 → 手机回到零状态
下次:     全部重来:新密钥对、新配对、新 SAS(这是特性,不是缺陷)
```

## 5. 密码学注意事项(实现红线)

- **不要整体引入 X3DH / Double Ratchet**:相关方有专利主张(Signal 对按其规范
  实现者授予许可,别赌)。本设计的"每会话重协商 + 会话内对称 KDF 棘轮"是
  有意绕开它们的,保持这个选择。
- HPKE 用成熟实现库(libsodium / hpke 库 / 平台 API),不要手搓 ECDH 拼装。
- nonce 绝不可重用:ChaCha20-Poly1305 的 12B nonce = 会话随机前缀 + 计数器。
- 随机数只从操作系统 CSPRNG 取;普通 random 是致命错误。
- 优先做测试向量与双端互操作测试;格式规范与向量随仓库发布。

## 6. UX 约束

- KPI 唯一:发一条加密消息 ≤ 正常发消息 + 1 步。每个交互都拿这把尺子量。
- 验证是安全地基,所以验证必须近乎无摩擦:大号 SAS 短码、当面扫码、电话念码。
- 不割裂原则:无深度链接、无主动行为;剪贴板与系统分享菜单是仅有的集成面。
- 移动端后期才做(分享菜单/键盘扩展是唯一允许的平台集成),v1 只做 CLI/桌面。

## 7. v1 验收标准

1. 双端进程完成 2 消息配对,各自显示相同 SAS(9 位数字)
2. 文本与文件往返加密,信道侧只见 base64/二进制,无明文泄漏
3. 会话退出后:进程内存清零,磁盘无新增字节(可用 strace/文件系统审计验证)
4. 错误输入(错口令场景不适用本项目;篡改密文/截断消息)→ AEAD 认证失败,
   永不产出错误明文
5. 实测 KPI 达标:发一条加密消息的敲击数 ≤ 平文 + 1
6. AGPL-3.0 完整 LICENSE 文件与源码头部署名

## 10. 已知风险(设计者须知)

- **验证纪律是最弱一环**:SAS 被跳过的会话=无认证裸奔。缓解:无摩擦验证 UX。
- 终端威胁与 IM 同机(截屏/输入法/剪贴板),与所有 E2E 工具同级;缓解:明文
  仅内存、短驻留、显式导出。
- 信道行为不可控:平台可能过滤大块 base64;缓解:低调格式、分片、必要时
  文件信道。元数据(谁/何时/多大)不在保护范围,如实告知用户。
- 战略风险:主流 IM 若原生上 E2E,本产品消费级价值蒸发——这是头号监控变量。
